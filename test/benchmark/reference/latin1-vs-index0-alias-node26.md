# Latin1 与 Index0：Unicode 别名及其他语料，Node 26

> 冻结实验记录（2026-11-15，Node 26.13.0 / M1 Pro）。文中工作区状态仅指测量时的快照。全部配对观测保留；JSON 中的 `$text` 在 [reproduction.json](reproduction.json) 的 texts 下按 SHA-256 查找。完整反汇编已裁剪，保留日志摘要、关键片段和原内容哈希。

当前 Latin1 为工作区的 main-fused-stream 逻辑。对照版本仅把 BlockLines.scan 的扫描器选择强制为 Index0，其他实现和容量准备不变。没有修改生产代码，也没有恢复已暂停的优化目标。

## 结论

连续别名会使两种策略都变慢，但本次 Index0 下降得更多。约 65,536 个字符的连续“上不”、没有换行时，Latin1 为 150～156 μs，Index0 为 614～620 μs，Latin1 用时约为 Index0 的四分之一。先前的 4.61%／9.27% 回退是相对旧的八路展开 SWAR，不是相对 Index0。

相同长度、同样没有换行的无别名中文，Latin1 约 15 μs，Index0 约 6.2 μs。换成全别名后，Latin1 约慢 10 倍，Index0 约慢 100 倍。因此不能据先前的别名回退判断 Index0 更适合这种输入。

Latin1 在真实换行较多的输入及本次中文别名输入上通常占优；没有别名、没有换行或行很长时，Index0 明显占优。这里是给定数据的观察，不是可直接推广到所有 Markdown 的选择规则。

## 方法

Node v26.13.0，arm64。两种策略都通过同一个 BlockLines API，复用行表；Latin1 的字符串复制计入时间，scratch 缓冲区复用。合成用例逐轮扫描长度 N 至 N+7 的八个字符串，真实文档扫描原文；表中时间已折算为单个文档。64K 表示 UTF-16 单元数，不是 UTF-8 字节数。

每项先完整核对所有行的 start/end/next 与换行规范化结果，再预热 100 ms、GC、稳定运行 50 ms、自然 GC 计时 200 ms。正序和反序各做四组 ABBA/BAAB，合计 32 个新进程；全部串行运行。A 为 Index0，B 为 Latin1。报告给出每个顺序各八次观测的耗时几何平均，以及配对耗时比。两种顺序都保留，避免挑选更好看的预热历史。

源码快照、构建脚本、测试脚本、输入哈希、原始观测和 95% 区间在同名 JSON。真实语料来自现有 test/corpus；中文段落是人工构造，不代表真实用户文本分布。本轮只测行扫描，不是端到端 Markdown 解析。

正序下，1M ASCII 短行的耗时变化为 -9.46%，95% 区间 [-28.27%, +14.27%]；Rust 为 -8.57%，区间 [-24.92%, +11.32%]。这些观测不能证明优势稳定。反序下分别为 -32.07% 和 -12.78%，区间均低于零。CommonMark 规格文档在两种顺序下都更快（耗时下降约 36%～41%）。

## 别名密度说明

正文 25% 别名用例重复“上不中文天地人和”，插入换行后全输入实际别名占比约 24.24%；连续“上不”插入 32 字符行宽的 LF 后为 96.97%。人工中文段落整体别名占比为 3.08%，最长连续别名仅一个字符。

这次没有用 V8 的原生字符串搜索 profile 证明 Index0 下降的内部原因，因此不将某一种底层搜索算法假设作为测量结论。
