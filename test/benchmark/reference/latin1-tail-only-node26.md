# Latin1 尾扫归一实验 — Node 26

> 冻结实验记录（2026-11-15，Node 26.13.0 / M1 Pro）。文中工作区状态仅指测量时的快照。全部配对观测保留；JSON 中的 `$text` 在 [reproduction.json](reproduction.json) 的 texts 下按 SHA-256 查找。完整反汇编已裁剪，保留日志摘要、关键片段和原内容哈希。

本轮选出 segment 候选；其后工作区又经历了 writeLine 等修改。结构简化与行为验证成功，但严格的“所有场景无回退”尚未达成；它仍是供审阅的实验候选。

## 方案

- 缓冲区向上补齐到 8 字节；复制前清零最后两个 Uint32，随后用真实输入覆盖有效部分。最多增加 7 字节缓冲区，不添加字符哨兵。
- 所有真实字符进入原 SWAR 事件循环；保留独立 EOF 行写入，没有逐事件 EOF 判断或越界 charCodeAt。
- 最后一块只为真实输入单位预留行空间。剩余真实输入能放入当前容量时，分段边界包含完整的补齐尾块。
- Latin1 类从 118 行减至 100 行，行字段写入组从三处减至两处。

## 测量方法

Node v26.13.0 / V8 14.6.202.34-node.40 / Apple M1 Pro arm64。基线是本轮开始时的工作区，已经包含用户的 crnext 命名和真值判断改写。

每组使用四个 ABBA/BAAB 配对块，共 16 个独立进程；扫描矩阵覆盖全部八种尾部长度，复用行表与 scratch，包含 Latin1 复制成本。每项 100 ms 预热、GC、50 ms 稳定、200 ms 自然 GC 计时。另以相反语料顺序运行，保留由不同预热历史产生的差异，不挑选较好顺序。下表是耗时变化，负数表示更快，方括号为 95% 配对区间；区间跨零不代表已证明性能相等。

## 其他候选

1. padded：固定预留八行，删除尾扫；部分精确容量输入提前扩容。正序连续 CRLF +2.56%，控制字符无换行 +1.85%。
2. bounded：按真实字符预留容量，并以真实 limit 控制循环；精确容量检查通过，但正序大段 Unicode +3.37%、长行 +2.23%。
3. reserved：恢复对齐循环边界，保留真实字符容量；大多数快路径接近持平，但控制字符无换行 +1.76%，256 字符控制项两种顺序均偏慢。
4. segment：在 reserved 上让最后一个分段按真实输入能否放下决定边界；作为本轮最终结构候选。并未将其认定为所有语料中性能最好的方案。

## 日志与结构性开销

计数插桩确认：默认容量的 64 KiB 无换行语料，基线与两种补齐候选都进入外层循环 15 次。构造容量为 4097 时，长度 65537 的 reserved 从基线的 16 次变成 17 次；segment 恢复为 16 次。这个修正是通用容量边界处理，但不能解释默认容量基准中的全部回退。

V8 trace-opt / trace-deopt / print-opt-code 压力序列中，无换行测量阶段前最新生成的 Latin1 TurboFan 内核：基线 8408 字节，reserved 6376 字节，segment 6408 字节。两个无换行测量阶段均未记录 deopt。热循环仍有原有的数组与字符访问检查，没有新增 EOF 事件处理；寄存器分配和代码布局发生变化。代码更小或没有 deopt 不等于更快，本轮尚未证明约 1%–2% 差异的具体运行时原因。
