# Fence 后续策略与占比目标

2026-11-18，Node **26.13.0** / V8 **14.6.202.34-node.40** / Apple M1 Pro arm64。

目标仍是 spec 中 fence 总占比约 **5%**，尚未达到。最新已采用按需根字面块直接输出，完整范围在计入迁移工作后约 **15.9%～16.5%**。原有范围约 14.7%～15.1%，不能用漏计根输出协议的数字验收目标。

已采用四项改进：JS 短头加原生 opening 扫描、关闭行的短行提前拒绝、纯 info 的合并检查、按需根字面块直接输出。各自相对冻结 A 的独立八块 spec 确认依次为 **−1.99% [−2.63%, −1.34%]**、**−1.31% [−1.75%, −0.87%]**、**−1.51% [−1.88%, −1.14%]**、**−2.60% [−3.10%, −2.09%]**。这些不是最终组合对最初实现的直接测量，不能相加。

[第一阶段](fence-path-model-node26.md)保留语法语言、坐标约束、工作量模型和六个初始候选。本报告的[配套 JSON](fence-followup-node26.json)保存后续源码快照、全部配对观测、验证结果和选定机器码。负数表示耗时减少；不同冻结基线的百分比不能相加。

## 占比和绝对成本

每次 parse 的近似模型是：

```text
T = T其他 + T识别 + T关闭 + T正文提取 + T代码节点构建
T关闭 = Σ各正文行 [条件检查成本 + 通过前置条件后的完整语法验证成本]
```

前置探测只能排除候选，完整接受仍须证明 `m^r · {SP,TAB}*`、`r ≥ k`，并精确抵达逻辑行末。既不能用首尾标记相等替代中间连续性，也不能把容器投影的列数当成物理偏移。

已采用 opening 版本的一次独立采样约为 705 µs/parse：

| 栈并集范围 | 占比 | 采样成本/parse |
| --- | ---: | ---: |
| fence.ts 及其被调用路径 | 10.43% | 73.75 µs |
| 再计入 fenced start / interrupt / codeFenceAt | 13.10% | 92.65 µs |
| 再计入共享 code AST builder | 19.63% | 138.76 µs |

最后一项包含 indented code 的共享 builder，是完整 fence 流程的保守上界。前两项也不是完整 fence 成本。采样包含 GC 分母，按 `timeDeltas` 加权，祖先命中只计一次；native 与内联归因仍可能不完整，不能把小数精度当成测量精度。

若非 fence 成本保持不变，当前占比为 `p`，目标为 `q`，则 fence 部分需要的加速倍数为：

```text
r ≥ p(1-q) / [q(1-p)]
```

以 `p=19.63%`、`q=5%` 代入约为 **4.64 倍**；只取模块范围则约为 2.21 倍。这是固定其他成本、固定归因范围下的推算，不是已测得的可达上限。把工作挪到行表生产者、漏计共享 builder，或者使其他解析变慢，都不能用来验收 5%。

采用短行检查后，另开进程按两种采样设置比较相同 bundle：

| 请求 / 实际中位间隔 | H 模块 → 新模块 | H 完整范围 → 新完整范围 |
| --- | ---: | ---: |
| 97 / 149 µs | 10.83% → 9.94% | 19.58% → 18.75% |
| 503 / 759 µs | 11.44% → 10.17% | 20.11% → 18.96% |

新版本完整范围约为 133～137 采样 µs/parse；这是诊断结果，不能作为吞吐时间。两组结果都明显高于 5%。旧轮请求 97/503 µs 的实际间隔约为 850/4,450 µs，不能假定请求值或旧实际值在后续运行中保持不变。

随后采用纯 info 路径，另开进程重新对照 L 与新版本 S：

| 请求 / 实际中位间隔 | L 模块 → S 模块 | L 完整范围 → S 完整范围 |
| --- | ---: | ---: |
| 97 / 149 µs | 10.09% → 10.08% | 18.76% → 17.22% |
| 503 / 759 µs | 10.16% → 9.98% | 18.94% → 17.13% |

S 完整范围约为 120～125 采样 µs/parse。核心模块成本没有明显下降；此次减少来自 info 的语义处理和分隔符检查。若以当前 `p≈17.17%` 重新推算，达到 5% 仍需该范围约 3.94 倍的加速，不能把这轮改进当成目标达成。

## 路径选择与机器码

opening 的混合策略保留 Rust 中大量短标记的 JS 拒绝路径，把长连续标记及禁止 info 标记的检查交给一个已编译的原生循环。没有为每个 opening 创建 RegExp 或缓存任意长度的模式。实体字符仍按 UTF-16 验证，Latin1 的低字节别名不能成为接受依据。

实际 arm64 正则代码的长标记循环仍是 `ldrh → cmp → branch → +2 bytes`，不是 SIMD。把 `{32}` 改写为 32 个字面量的原生代码仍是标量比较，反而从量词探针的 1,352 字节增到 1,704 字节，因此没有继续引入动态长度正则缓存。

字节借用的早期版本按 `.buffer` 比较身份。反汇编明确包含两次 C++ `get buffer` 调用；改为字段数组自身的指针身份后，这些调用消失，JS 代码从 6,056 缩至 5,776 字节。但完整 spec 仍慢约 0.93% / 1.76%，没有采用借用和释放协议。

`StringEqual` 内建含有相同宽度字符串按 64 位块比较的分支。切片是否能使用该分支，还受间接字符串表示、解引用及 runtime 路径影响。实际新增的前缀切片、相等检查和精确行末快捷返回没有带来稳定收益；`startsWith` 版本慢约 4.83%。这验证了机器码只能提出候选，完整测量决定取舍。

关闭标记的下一项低复杂度候选是先检查 `lineEnd-lineStart < k`。这是必要条件：合法标记位置不小于行首，所以长度不足的行不可能闭合。原有缩进后的边界检查仍然保留。

独立插桩对 spec 的 4,876 次检查得到以下交集：

| 原始行长 / 首字符 | 其他 | 空格 | 标记 |
| --- | ---: | ---: | ---: |
| 小于 opening 长度 | 3,376 | 286 | 75 |
| 足够长 | 354 | 80 | 705 |

前置行长检查可省去 **3,737 次、约 76.6%** 的首字符读取，并减少后续缩进与边界检查；代价是每次都先读取行末。对两个必要条件，若成本近似恒定，先检查 `A` 的模型为 `cA + P(A)cB`，先检查 `B` 为 `cB + P(B)cA`；应比较单位拒绝概率的成本 `c/(1-P)`。这里两条件的拒绝率接近，关键是行表整数比较与 UTF-16 字符读取的实际生成代码成本。该模型不包含分支预测、寄存器压力和内联变化，仍须配对测量。

这一候选的首轮 spec 为 **−1.71% [−2.75%, −0.65%]**，独立八块确认 **−1.31% [−1.75%, −0.87%]**；document/spec 确认为 −1.50% [−2.20%, −0.79%]。examples、Rust、APIs、tail 的区间均跨零，tail 点估计为 +1.48% [−0.81%, +3.83%]，不能据此证明其他场景没有回退。自然执行中，V8 同时改变了内联选择，fenced start 机器码由 8,056 增至 11,528 字节，并内联了 appendFencedToken。不能把收益单独归因于指令减少。该候选只移动一个必要条件，未增加元数据或跨模块协议，已采用。

完整摘要缓存的 classifier 自身约 72 µs/parse。即使读摘要一侧变快，把 classifier 算回后模块范围约为 15.41%，而非 5%。旧采样器只显式纳入了 classifier helper；当前脚本对这些缓存方案保守地纳入整个 physical scan，以覆盖内联到生产者的其他工作。

UTF-16/SWAR 内核通过了 1,966,080 组数值对和 703,453 行几何校验，但复制与扫描成本使全量 parse 更慢。逐行整块正则的初稿还存在缩进 closing 错误：验证失败记录保留，停止后的失败计时文件没有完成观测，未纳入收益表。修正版重新通过验证后仍慢约 11.19%。

run 末端候选用 `m+(?=[ SP TAB ]*(?:CR|LF|EOF))` 保持 `lastIndex` 停在连续标记末端，然后比较动态 `k`。它依赖现有投影行保留物理行末的约束，通过了两后端差分验证。关闭正则从 1,208 增至 1,296 字节，省去 JS 的末标记读取仍未检出收益，因此保留原有实现。

info 正则提升候选在两后端分别通过扩展后的 6,162 份文档、7,060 次编辑对照。baseline builder 的实际代码把 young-generation top 增加 `0x38`，写入 RegExp map、数据、source 和 lastIndex；提升后直接加载共享 RegExp，函数从 5,732 缩至 5,612 字节。已证明省去这次 56 字节分配，仍未检出完整 parse 收益，未据此宣称 GC 或吞吐改善。

提前 AST 的修正版同步推进 locator 到已知物理结束行，避免后续位置查询继续走过正文。两后端各通过 6,165 份文档、7,060 次编辑及节点/位置独立所有权校验，spec 仍未检出稳定收益，未采用额外的提前构建模式和 locator 协议。旧坐标 helper 在 append 中被内联，没有找到早期 `.buffer` 路径那种 getter 调用证据，因此也未盲目增加 row-base 缓存。

header 缓存仅保存一条已验证的长 run（探索阈值 16）及至多 128 UTF-16 单元的完整 header，完整文本相等才复用 run 长度；位置和 AST 保持每次创建。V8 原生探针和堆边显示，短拼接再切片的副本保留 104 字节的短母串，原切片保留的母串为 12,176 字节；该探针保持 two-byte 表示。此结果不意味着其他引擎或未来版本也采用该表示。两后端差分和所有权校验通过，但主场景四块没有收益，因此没有继续测其他吞吐场景，也没有采用共享缓存状态。

四字符原生循环把剩余 run 表示为固定前缀后接 `(mmmm)*m{0,3}`，完整覆盖合法长度，禁止 info 标记的检查仍防止接受非最大 run。关闭时复用已证明的首标记，从下一字符开始扫描。实际循环每轮推进 8 字节，包含四次标量 `ldrh`；opening/closing 原生代码分别由 1,408/1,208 增至 1,824/1,600 字节。首轮约 −1.08%，独立八块确认的区间仍跨零，Rust 点估计 +0.87%，未采用。

## 纯 info 路径

把原始 info 中的复杂字符集合定义为 `{反斜杠, &, SP, TAB}`。若不含这四类字符，`semanticText(info)=info` 且分隔符位置为 −1，因此可以直接得到 `lang=info||null`、`meta=null`；含复杂字符时完整沿用既有解码和分隔逻辑。实体解码可能引入空白，所以 `&Tab;`、`&#32;` 必须进入回退路径。

原路径先查询反斜杠、再查询实体符号，再搜索语言分隔符。新路径用一条共享、非 global 的正则完成常见情形分类，既不缓存输入，也不共享 AST。实际 builder 从 5,732 缩至 5,352 字节。对旧 L 采样作栈并集拆分，code AST 约 45.63 µs/parse，其中 semanticText 约 7.79 µs；这用于选择实验方向，不把每个采样标签当成独立因果成本。

该候选首轮 spec −1.19%，独立八块确认 **−1.51% [−1.88%, −1.14%]**；document/spec **−0.74% [−1.38%, −0.10%]**，Rust **−0.96% [−1.41%, −0.50%]**。examples、APIs、tail 的区间跨零，不能证明没有回退。两后端各通过 6,165 份文档、7,060 次编辑和字面节点/位置独立所有权检查，采用后 199 项测试、typecheck 和修改文件 lint 通过。

另一候选只缓存一条不超过 12 单元的 info 解析结果，缓存键用 split/join 做短副本，结果仅含不可变字符串或 null。它没有稳定超过零收益，且引入状态和复制，因此选择无缓存路径。延后构造 AST 的候选保持 value→position 的求值顺序，确实把 64 字节代码节点分配移到查询之后，builder 再缩至 5,076 字节，但完整 spec 几乎无变化，未采用。

## 新前提的筛选与分配检查

将纯 info 分类融合进 opening，并传递提示给 code builder，确实覆盖了 spec 的 708 个已接受 opening，但完整 spec 的四块区间跨零。该方案增加 Fence、token metadata 和 builder 间的协议，未采用。分类计数由独立插桩获得，不参与计时。

另一个实验把实际 opening 长度写入闭合搜索的原生模式，用有界六项缓存避免无限增长。最初的 `{k,}` 版本在 k=32 时仍逐 UTF-16 单元推进，未产生预期跳跃，因此没有运行吞吐比较。随后用物理换行前缀加 k 个字面标记，实际 k=32 机器码出现 128 字节查表和失败时推进 16 字节的搜索循环，即每次跳过 8 个 UTF-16 单元。正向验证仍有标量比较，并不能称作 SIMD；完整 spec 慢 2.45%，未采用。两版都保留投影行回退，并在 generated/CSP 各通过 6,165 文档、7,060 编辑和对象独立性检查。

提前构造物理节点的新版传递八个标量参数，把代码节点与位置图放入同一对象字面量。实际 `createPhysicalCodeLiteral` 的空间上限检查为 `top + 0xc8`，覆盖 64 字节代码节点、40 字节 position、两个 48 字节 location，共 200 字节。**合并的是分配空间检查，仍保留四次 allocation-top 写入及各字段初始化**，没有减少对象数。首轮 spec −1.37% [−2.34, −0.40]；独立八块 spec −0.52% [−1.30, +0.27]，document/spec +0.52% [−0.04, +1.09]，其他四场景区间也跨零，因此不采用六文件协议。

更小的单文件候选先计算两个坐标，再创建 position/start/end 三对象。实际 `positionAt` 有 `top + 0x88` 的 136 字节合并空间检查，仍有三次 top 写入，函数 2,360 字节；完整 spec 未检出收益。两种分配候选都通过上述两后端差分和独立所有权检查，保持生产实现。

精确 UTF-16 候选移除了旧摘要预计算，行生产改为 UTF-16LE 副本及 16 位 SWAR 换行检测，闭合行按对齐的 32 位字比较两个标记，并完整验证 run、缩进、尾部和逻辑行末。原始 UTF-16 单元保持不变，不能使用 Latin1 低字节别名接受。借用只在最新物理行表身份相同时有效，扫描结束释放；投影和无借用场景回退现有实现。独立内核检验再次通过 1,966,080 对和 703,453 行，两个完整后端均通过差分和对象独立性检查。实际闭合函数 2,056 字节，包含 `ldr w..., [base,index,lsl #2]` 的成对读取；完整 spec 仍慢 10.06%，不采用。不能把每轮比较两个字符直接当成整个解析器加速两倍。随后仅更换 UTF-16 行生产、保留原 fence 检查的独立拆分对照，spec 慢 10.38% [9.73, 11.04]；结果支持数据生产是这一方案的主要障碍。两次独立测量的差值不能作为闭合内核收益的精确估计。

## 按需根字面块直接输出

固定字面量 `startsWith` 的隔离探针（为观察独立函数关闭内联）生成 2,912 字节 TurboFan 代码，仍按单个 UTF-16 单元比较并分派字符串表示；没有据此加入固定长度分支。搜索首个非 marker 的原生否定字符类也仍逐单元推进。探针用于筛选机器码前提，没有当作完整吞吐比较。

新候选减少真实中间工作：顶层 code/math fence 在扫描时产生本次拥有的完整 AST，省去该节点的 token 字段写入、metadata 包装和后续 builder 分派。其他根块仍先记录 token，扫描完成、定义表齐备后再构建。输出数组保存 token 下标或已构建节点，构建结束才成为返回的 children；每次 parse 都是新数组和新位置图，不缓存 AST，也没有延迟位置查询。

初稿把物理连续误认为根所有权。组件正文通过 `lines.view` 借用物理子范围，导致内部 fence 错误逃逸到根层。反例 `::card\n```\nbody\n```\n::\n` 已确认，独立计时在发现后以退出码 130 停止。两个错误快照、已完成主场景计时和未完成确认均保留，标为不可用于采用决策。新矩阵加入 54 个组件、slot、嵌套容器和换行组合，generated/CSP 各达到 **6,219 文档、7,168 编辑**，并继续检查完整 AST、位置及独立所有权。

修正版只允许 `lines === context.directLines` 的根行表输出。主动收集每个根块的版本独立确认 spec −2.37%，但 examples +3.34% [2.27, 4.43]、Rust +0.72% [0.06, 1.39]，因此未采用。最终版在首个根字面块出现时才把已完成的根 token 下标收集到输出数组，随后按需收集；没有可直接输出根字面块时沿用原构建循环，不再添加逐根块 callback。

令 F 为可直接输出的根字面块数，R 为总根块数。成本模型省去 F 次 token/metadata/builder/位置遍历，增加按需下标收集和输出类型判断；F=0 时不构造混合输出序列。没有给这些项虚构固定纳秒系数。独立诊断在 spec 得到 R=1,418、F=688，token 从 2,867 减至 2,179；组件内字面块继续留在其 token 树中。返回值、位置图和正文提取仍完整执行。

自然执行的 `createPhysicalCodeLiteral` 为 1,040 字节，具有 `top + 0xc8` 的 200 字节统一空间检查，仍有四次 top 写入。主要新前提是删除中间 token/包装及通用分派。首轮四块 spec −2.82% [−3.47, −2.16]，独立八块结果：

其余区间跨零，不能据此证明没有回退。候选源码通过 199 项快照测试及类型检查；工作区补充组件与根 fence 交错、重复 parse、增量编辑的回归后，**200 项测试 / 16 文件、typecheck、所有修改文件 lint 通过**。快照测试的加载清单确认覆盖全部七个修改运行时文件。格式化后的生产 bundle 与测量的 lazyDirectRoot **逐字节哈希一致**，对应关系保存在 adoptDirectRoot 的 adoption-equivalence.json。

## 短行分组、模式前缀和 info 提前提取

以 D 为冻结基线，另外比较四个候选；均未采用，也没有对区间跨零的结果反复确认直到有利：

| 候选 | spec 耗时变化 [95% CI] |
| --- | ---: |
| 行表内部连续跳过短行 | −0.25% [−1.57, +1.09] |
| 分组跳过，并删除闭合函数内的重复长度快拒绝 | −0.55% [−1.37, +0.27] |
| 有界、与输入无关的同宽 delimiter 模式缓存 | +0.64% [−0.20, +1.49] |
| 提前取得 info，原生单字符查找检查禁用标记 | +0.22% [−0.74, +1.20] |

四者分别通过 generated/CSP 的 6,219 文档、7,168 编辑和独立所有权检查、完整 200 项快照测试、59 个应用源文件的类型检查。加载清单与快照哈希验证覆盖各自全部修改文件。它们的计时、源码和检查记录都保留。

短行版不增加行预计算或字段，将数值长度拒绝集中到 `BlockLines.skipShortLines`。独立计数得到 3,737 条短行被跳过，完整验证源码入口由 4,876 降至 1,139，跳过 helper 也进入 1,139 次；该份 spec 没有耗尽行视图的分支。保留重复长度快拒绝的版本又多检查 1,139 次必要条件，因此另做了删除该快拒绝的拆分对照。删除不影响语义：后面的 `offset+k-1 >= lineEnd` 和标记探测仍保证最小 run 边界，组件等其他调用方也保留完整语法验证。

源码入口数不是机器调用数。自然执行中 D 的 closesFence 和新 skipShortLines 都被内联；包含新内联体的生成 dispatch 函数为 10,776 字节。模型中应比较重复字段/条件检查、循环结构和内联上下文的变化，不能假设省去 3,737 次原生函数调用。完整测量未检出稳定收益，未增加该行表 API。

模式缓存每条规则最多保留主/替代 marker 各一条、16～128 UTF-16 单元的纯模式字符串，由 marker 和长度构造，不保存输入。Unicode 前缀再切片使本机值保持 SLICED_TWO_BYTE_STRING_TYPE；超过边界回退原生验证。它与旧的逐 opening 输入切片前缀不同，避免了重复构造比较模式，但仍需创建待比较切片、增加 Fence 字段和缓存查询。90 次独立边界/交替 marker 检查通过；完整 spec 没有收益，未采用状态。

对本机 Node 可执行文件做离线 LLDB 反汇编，没有启动或附着进程。`StringSearch<unsigned short,unsigned short>::InitialSearch` 的正向校验仍是两个 ldrh、比较、索引加一；memchr 用于首字符查找，dup/str q 位于查表初始化，不能把这些指令认作完整模式的 SIMD 校验。因此没有再实现等长切片 indexOf 比较分支。二进制 SHA-256、符号名、命令和完整相关反汇编已归档。

info 版将 opening 正则缩为最大 marker run，再取得已裁去 SP/TAB 的 info 字符串，用其 includes 检查禁用标记，并把同一字符串传给 append。单字符搜索被限制在 info 内，不扫描正文。当前两次自然诊断中，opening 正则原生代码由 1,408 缩至 1,024 字节，fenceAt JS 代码由 2,352 增至 4,488 字节；关闭正则仍为 1,208 字节。代码大小变化不构成因果速度证明，完整 spec 结果跨零，继续保留 D。

## 构造器的字符串类型与坐标检查

又以 D 为基线验证五个快照，均未采用。源码改动全部局限于构造路径，不缓存输入或 AST，不改变节点属性顺序，不延迟位置计算。新检查入口将两后端差分、类型检查和完整快照测试串行执行，任一步失败即停止；五者均通过 6,219 文档、7,168 编辑/后端、59 个应用源文件类型检查和 200 项测试，加载路径与快照哈希也验证通过。

| 候选 | 物理 Code 构造器字节数 | spec 耗时变化 [95% CI] |
| --- | ---: | ---: |
| D 基线 | 1,040 | — |
| info 以 length 判空 | 832 | 独立八块 **+0.57% [+0.13, +1.01]** |
| 六坐标入口转为 int32 | 1,176 | +0.14% [−0.29, +0.56] |
| 字符串入口类型化 | 840 | −0.12% [−0.50, +0.25] |
| 字符串与入口坐标组合 | 976 | 未计时，机器码对照 |
| 将组合版坐标转换延后至 info 处理之后 | 904 | −0.13% [−0.63, +0.36] |

info 的内部契约是原始字符串，空串真假与 length 为零等价。将物理和通用 Code builder 的 `info||null`、`if(info&&...)` 改为 length 条件，确实减少了通用真假值分派。但首轮四块 −0.28% [−1.54, +0.99] 没有稳定收益。由于构造器机器码缩小 20%，在查看首轮摘要前记录了一次六场景、独立八块确认计划；确认并未改善 spec，不能以函数更小决定采用。其余确认结果均跨零：document/spec −0.07% [−0.57, +0.43]、examples −0.24% [−1.14, +0.66]、Rust +0.52% [−0.49, +1.54]、APIs −0.92% [−2.47, +0.65]、tail −0.69% [−1.94, +0.58]。没有继续重复确认。

坐标候选先证明转换精确：本机 Node 的 MAX_STRING_LENGTH 为 536,870,888；物理根行的 offset 在 `[0,N]`，line/column 至多 `N+1=536,870,889`，均为精确整数并小于 2,147,483,647。六个参数由原有 Int32 行几何产生，包含虚拟 EOF 行，因此此处 ToInt32 不损失坐标。没有为验证上界分配大字符串。

入口坐标转换将六个 Smi 检查移到对象分配之前，实际省掉两个 location 对象的六次默认字段写入。但它让六个中间整数跨越 info 的原生正则调用：实际代码出现调用前六次写栈、调用后六次读栈，局部栈空间由 16 增到 64 字节。减少堆字段写入并不等于减少全部存储工作，完整 parse 未检出收益。

字符串候选只在物理构造器入口对 value/info 加空串。内部参数均已是字符串，值不变；自然优化代码没有留下实际 StringAdd/ToString 调用。它缩窄字符串数据类型，去掉 Code 的 lang/meta/value 三次默认字段写入，但完整 spec 仍无稳定收益。

组合版省掉九次默认字段写入，但仍有过长的坐标活跃区间，因此只保留机器码对照，没有声称吞吐。随后把六次坐标转换移到 info 语义处理之后、对象字面量之前，实际消除了正则调用附近那组六写六读，构造器从 976 缩到 904 字节。组合前后仍保留 48 字节局部栈空间，不能宣称整个栈帧回到基线；慢分配路径仍可能需要栈槽。延后版的完整 spec 区间仍跨零，未采用。

五版的完整图仍为 Code 64、position 40、两个 location 各 48，共 200 字节，统一空间检查和四次 allocation-top 写入保留。这里证实了检查与存储指令变化，也证实了这些变化不足以支持完整解析加速结论。当前生产仍是 D，完整范围占比没有新的下降证据。

## 内联复核与共享原生候选序列

关闭并发重编译的干净诊断给出物理 Code 构造器的字节码长度 **247**；当前单函数内联上限是 460，日志明确记录它内联到 appendFencedToken。单函数上限不是内联保证，累计预算和反馈仍影响选择，但这次记录已经反驳“构造器过大而不能内联”的前提。因此没有继续实现无依据的冷分支拆分。独立构造器的机器码不能代替实际调用上下文的判断。

在已由 `lines===context.directLines` 保证根行表的路径中，另试直接用 `start+1` 计算行号，并删除不再需要的 physicalRowIndex helper。其他视图继续走原 token 路径，回归用例覆盖组件借用视图。appendFencedToken 的一次干净诊断从 5,216 缩到 5,160 字节；完整 spec **−0.05% [−1.16, +1.08]**，未检出收益，未改入生产。

更大的候选用一条 global 原生正则扫描物理 code/math 标记行，`.test` 的 lastIndex 给出最大 run 末端，不创建 exec 匹配数组；按序合并原行表，保留 row、markerOffset、runEnd、marker/closing 位的 Int32 记录。序列只在首个有效根 fence 时建立，每次 parse 重建逻辑长度和游标，容量复用；不缓存完整输入或 AST。后续根 opening 复用 run 与合法性结果，closing 在候选中验证 marker、动态最小长度和空白尾部。组件、引用、列表视图和增量文档保留原路径。

首版以物理行首的否定后顾约束定位，独立插桩得到一次构建、1,453 个候选、689 次 opening 查询、688 次 closing 搜索。完整 AST 与基线相等，确认新路径实际执行。然而 spec **+38.26% [+37.06, +39.47]**，淘汰。

拆分版消费 CR/LF/CRLF 前缀；首个 opening 已由原解析验证，搜索从其行首开始，只收集后续候选。候选为 1,452 个，其余查询数不变。它同样正确，但 spec **+25.93% [+24.38, +27.50]**，仍淘汰。没有继续重复确认或调整阈值以追逐该语料。

机器码也校正了对搜索循环的猜测：首版原生代码为 4,048 字节，初始失配搜索循环已经按 4 字节、即 2 个 UTF-16 单元跳过；消费换行版为 7,392 字节，对应初始循环按 6 字节、即 3 单元跳过。两者都有其他标量 run/回溯循环，不能把写法直接解释为没有跳步或 SIMD，也不能把两个独立对 D 的百分比相减当作配对收益。

成本模型变为：

```text
T候选序列 = T全段原生搜索(N,E) + T行表合并(R,E) + T尾部分类(E)
            + Topening查询(F) + Tclosing候选遍历(E) + T原正文/AST
```

候选虽少于正文行数，却增加了一遍文本扫描与行表合并，不能把已付过的行生产成本当成免费预计算。消费换行版另开诊断进程，请求 211 µs、实际中位 320 µs、4,007 次 parse，计入迁移工作后的完整范围为 **31.95%**、约 **280.5 采样 µs/parse**；其中 build 标签的 self 约 **206.7 µs/parse**。这些包含 native/内联归因限制，不是逐条指令时间或吞吐收益，但足以显示新构建阶段不能从 fence 成本中排除。

三个候选均通过两后端 6,219 文档、7,168 编辑及所有权验证、59 个应用源文件类型检查和 200 项快照测试。源码、完整配对观测、计数器、机器码及剖析摘要均归档；当前生产仍为 D，5% 目标尚未达到。

## 根路径融合：局部状态代替描述对象

新的候选 E 仅在 `lines===context.directLines` 时使用一个共享 code/math 解析函数。它保留原生 opening 和 closing 的完整验证，借用现有 Int32 行表扫描结束行，并直接完成正文、info、位置和根 AST 输出。marker、length、closingPattern 和 indent 保留为局部状态，不创建 JS Fence 描述对象；嵌套、组件借用视图和 indexed 路径继续使用通用 token 协议。行表仅在本次同步调用中读取，不保存输入或借用视图，也没有第二遍全文预索引。

根表从偏移零开始，所有行的投影前缀为零，因此行号等于 `start+1`。关闭标记前若出现 TAB，列数至少为 4，已不属于合法缩进；根路径的缩进探测因此只需接受 0～3 个空格。这项特化不能推广到组件等物理子视图。结束位置仍按最后消费行、闭合状态及虚拟 EOF 的同一公式生成，正文沿用原提取器。

将 F 次根块的中间状态和协议成本单独写出：

```text
T_D = T其他 + F·(c入口 + c描述状态 + c通用append)
      + Σ正文行 c关闭检查 + T正文/AST/输出
T_E = T其他 + F·c融合入口
      + Σ正文行 c融合检查 + T正文/AST/输出
```

这没有假定每个源码调用对应机器调用，也没有预设对象分配必然发生：内联和逃逸分析可能已经消去部分成本，新的融合函数也可能增加寄存器压力、代码体积或反馈多态。必须比较完整机器上下文及端到端基准，不能把删除的源码对象数量直接乘以一个臆定的纳秒常数。

干净诊断中，parseRootFence 的 TurboFan 代码为 **11,512 字节**，内联了 borrowedFields、正文提取、Code 构造器、emitDirectBlock 和 appendDirectTokens；该函数自身因字节码限制未被上层入口内联。预热期发生一次 wrong-map 的 Maglev deopt，settling/diagnostic 期没有它的 deopt 记录。这些只描述该诊断进程，不保证每个吞吐进程选择相同代码，也不把较大/较小的机器码直接当成性能结论。

第一版同时删除了通用 append 的可选节点构造协议。首轮 spec **−2.42% [−3.29, −1.55]**；独立八块确认 spec **−1.74% [−2.01, −1.46]**、document/spec **−0.42% [−0.77, −0.07]**，examples、Rust、APIs 区间均跨零，但增量 tail **+1.30% [+0.15, +2.47]**。因此拒绝该快照，没有以 spec 的收益覆盖 guard 回退。后续隔离版保留 D 的通用 append、调用者和 physicalRowIndex，仅在根入口增加提前分支，作为独立源码候选验证；不能预先断言前次回退的原因。

隔离版的另一次干净对照得到同样的融合函数大小 11,512 字节；基线 fenced start 为 9,336 字节。在基线内联 fenceAt 的 opening 之后、closing 循环之前，确实存在独立的 **64 字节** Map[64] 描述对象分配及五个属性写入。融合路径消除了这一中间对象，保留了后面的 **200 字节 Code AST 图**分配。这比按源码推测分配更有依据，但只对该优化上下文成立；两个不同函数的字节数也不能当作总代码占用直接相减。

隔离版首轮 spec **−2.45% [−3.73, −1.16]**、tail **−0.71% [−2.18, +0.79]**。独立八块确认 spec **−1.48% [−1.99, −0.97]**，document/spec **−0.03% [−0.72, +0.66]**，examples **+0.69% [−0.67, +2.07]**，Rust **−0.47% [−0.97, +0.03]**，APIs **−0.50% [−2.20, +1.23]**，tail **+0.65% [−0.79, +2.12]**。guard 区间跨零不能证明没有回退。用户转入同步上游和逐项审查，因此该快照保留为待审实验，未加入工作区 D，也尚未测量完整流程占比。

## 验证、记录与回放

吞吐、诊断、正确性验证串行执行。ABBA/BAAB 交替块，每个观测为独立 Node 进程，250 ms 预热、full GC、150 ms settling、约 300 ms 自然 GC 计时。探索用四块，选中方向另用独立八块确认；统计按逐块 log ratio 和 Student-t 95% 区间。未删除不利观测，也不拿诊断耗时充当吞吐收益。

前两项已采用改进在 generated/CSP 两后端分别通过 **6,145 份文档、7,026 次编辑**的完整 AST 和位置对照；纯 info 版本扩展至 **6,165 份文档、7,060 次编辑**，并检查独立所有权。编辑结果也与 fresh parse 比较。覆盖 code/math、CR/LF/CRLF、容器投影、缩进、长 delimiter、非法中间缺口、Unicode 低字节别名及等长度但行几何变化的编辑。最新 D 的工作区 200 个测试、typecheck 与修改文件 lint 通过。差分验证证明与冻结基线一致，不把继承语法行为认定为独立 CommonMark 正确性证明。

研究脚本已从 1,316 行收缩至约 300 行，只保留快照构建、回放、验证和剖析。已淘汰方案的生成器移入 JSON，不再作为当前脚本的可选生产路径。当前 69 个实验目录全部重建得到相同 bundle 哈希；其中三个包含失败候选，一个为独立计数诊断，两个仅完成机器码筛选，一个为最终格式化/采用校验。完成的 75 个配对文件保留 200 个场景比较、4,256 次独立进程观测；错误候选的完成观测和中断确认均单独标明，不能当作有效收益。

JSON 中 `texts[sha256]` 保存 UTF-8 原文，`snapshots[id]` 按路径引用文本；`trials[id].sources` 指向完整运行时快照。每个配对文件的 A/B 快照单独记录，防止错误复用基线。保留全部完成的配对观测和选定 fence 函数/regexp 机器码；其余完整 trace、bundle、source map 和原始 cpuprofile 仅在本机缓存中，哈希不能替代内容。
